# Estado general

## Planes respecto a las offers queries de Epic

### Situacion actual

Las queries a la API GraphQL de Epic son bloqueadas sin son realizadas desde un backend cloud.
Solo funcionan desde local.
Esto causa que el enriquecimiento de la BDD llegue con datos vacíos en los campos de precio y tags (meta-tags no son suficientes)

### Opciones

Ahora mismo hay 2 opciones para llenar los campos vacios:

1. Correr el servicio _epic-offers-bridge_: Automatiza el proceso, pero solo funciona en local. Ayuda si un dev conecta una cuenta, evitando tener que correr un script posterior al import. Muy limitado (a menos que un dev tenga muchos juegos)

2. Cron job con un script de curación: Se puede dejar corriendo un script local que periódicamente revise si hay entradas con los campos que la offers query rellena. Luego, los actualiza. Esto debería resolver bien el problema en principio, pero deberíamos apuntar a automatizar completamente el proceso para evitar inconsistencias. Ej: Usuario importa librería de epic, pero no tiene tags y precios de inmediato -> Afecta su experiencia y su primera impresión ( a pesar de que en su próxima visita deberían mostrarse ) Un parche puede ser mostrar "Información disponible en x tiempo" (asociado al periodo del cron job). Hay que considerar también que el parche de datos requiere un manejo más fino de caché. Si un juego llegó con datos incompletos ¿Cuando triggereamos una nueva consulta a la bdd?

Otras opciones pueden ser exploradas. Quizás usar un proxy pueda solucionar todo, pero esto requiere más investigación y planificación.

## Consistencia de precios

Los precios y especialmente ofertas, están cambiando constantemente. No podemos confiarnos completamente en guardarlos en la base de datos y que ahí queden.
Se puede aprovechar la idea del cron job del punto anterior para revisar precios de los juegos en todas las tiendas.

Aunque la frecuencias de estas consultas es mucho menor, el volumen de datos es mucho mayor, por ello hay que tener cuidado con los rate limit y aprovechar las consultas en bulk.

Requiere investigar la frecuencia de actualización de precios de cada tienda para establecer el periodo más óptimo.

## Otros datos faltantes

La pipeline actual de extracción de información desde las distintas API funciona bien en general, pero no entrega correctamente todos los datos. Hay varias entradas con imágenes rotas, requirements faltantes o descripciones inexistentes. Esto con mucha seguridad representa casos borde en algunos juegos, donde la información está en campos distintos.

El plan sería un script que analice la bdd, detecte aquellos juegos con campos faltantes y debuggear las respuestas de la pipeline con ellos, para así ver que es lo que ha fallado.

## Mejoras en Steam

### Grupo familiar

Muchos jugadores formar parte de un grupo familiar y la consulta sobre la biblioteca del usuario no retorna estos juegos. Una revisión de las apis publicas de steam verifica que existen formas de obtener formas del grupo familiar al que pertenece el usuario y quienes forman parte de él. Una consulta cruzada a esos user puede entregar esos juegos en principio (limitado por cuentas privadas). Se puede seguir investigando para evaluar una forma más directa de obtener esos juegos, pero por ahora el método descrito se ve lo suficientemente robusto.

### Cuentas privadas

No hay mucho que hacer en este caso, es lo mismo que pasa en Epic.
Aún no tengo claridad si un usuario con su cuenta privada trata de importar sus propios juegos tendrá problemas con eso. La API key es de mi cuenta personal, pero el usuario está haciendo consulta a su propia steam_id. Es un caso que hay que verificar.

Para todos los casos de cuentas privadas, es necesario exponerlo claramente en la UI. Un amigo con cuenta privada devolverá una lista de juegos vacía. Se debe mostrar esto explícitamente para que el usuario sepa porqué los juegos no están siendo mostrados.

### Juegos NSFW

Steam es la única tienda con juegos que pueden tener esta clasificación, y puede ser incómodo para un usuario que estos se importen directamente (además, pobla nuestra base de datos). Es necesario tomar una decisión de como manejaremos este tipo de juegos. Algunas opciones son:

1. Importar siempre, pero dejar imagenes "blurry" en la carga. Poner aviso al hacer click para ver mas detalles.
2. Configuración. Poner un toggle NSFW desactivado por defecto. El usuario decide si quiere importarlos o no.
3. Nunca importar

## Specs

En este momento la funcionalidad de chequeo de specs no está muy trabajada.
Esto requiere mucho input manual y es confuso para usuarios no expertos. Además, la función no está claramente indicada. User puede no darse cuenta que clickeando un juego abre modal de specs.

### Ideas de mejora

- Detección automática de hardware: Opción directa y sencilla usando algún paquete. User no tiene que ser experto ni saber que tiene. Podría requerir consentimiento.
- Simplificar selección de specs: En lugar de seleccionar cada componente manualmente, podemos establecer una tier completa de setup. Tipo low end, mid end, high end.
- Mantener selección de hardware específico como un "modo avanzado"

### Desafios

Si el setup del usuario es definido de forma específica (por ejemplo con detección automática) es necesario implementar un mecanismo de comparación. ¿Como sabemos que el setup actual cumple con los requisitos del juego? Podría requerir una nueva bdd o una API externa.

### Ubicacion

Ahora mismo la verificacion de hardware aparece al clickear la tarjeta de un juego en matching, pero uno esperaría ver ahí información del juego.

Al menos, la selección de specs debería moverse a otro lugar donde tenga más sentido. Una idea puede ser, en el pool de amigos seleccionados. Eso hace más cómodo establecer specs para amigos no registrados (simplificado por tiers y/o selección de hardware específico i.e. modo avanzado)

## Mejoras en UI/UX/QOL

### Mejor feedback visual

Al completar acciones importantes, como conectar una cuenta o cumplir requisitos de matching, el feedback debe ser claro, con animaciones idealmente.

Se espera que el feedback guíe al usuario por el flujo del sitio, para que lo complete sin inconvenientes.

### Game cards

Se mencionó un poco en el punto de Specs/ubicacion. El plan es rediseñar lo que se muestra al hacer click.

Como el contexto de la game card es "juego que todos tenemos" pero "no necesariamente lo hemos jugado todos" debe tener información que resuelva las dudas que se puedan presentar:

- ¿De que se trata? (descripción, categorias)
- ¿Es bueno? (reviews, rating)
- ¿Como se ve? (imágenes, videos)
- ¿Lo podemos jugar? (requirements validation)
- ¿Cuantos puedes jugar? (cantidad de jugadores)
- ¿Que tanto podemos jugar? (DLC por usuario)

### Filtro rápido

Funcionalidad simple para asignar todos los filtros cooperativos/multiplayer.
Ya que el user llega al sitio buscando eso, queremos que la opción esté directamente accesible.

### Buscador/order en friends

Para grandes listas de amigos. Un filtro y ordering para encontrar a un amigo rápidamente

### Profile imgs

Ahora mismo las imagenes de perfil de los amigos no se obtienen. Esto haría la sección de matching más variada.

### Repensar multicuentas

Amigos con multiples cuentas en una misma plataforma o cuentas en varias plataformas. El primer approach fue hacer un merge arrastrando las tarjetas de usuario, unificando identidades juegos adquiridos. En principio esto debería resolverse si el amigo existe en la bdd, pero muchas veces no será así. La idea del arrastre funciona, pero puede ser incómoda. Se debe buscar una manera más cómoda para el usuario.
